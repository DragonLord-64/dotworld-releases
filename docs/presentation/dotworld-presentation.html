dotworld · 01

Where it lives

dotworld does not host your repository. It adds one directory to it and leaves every other byte alone.

shown: emberfall — a C++ game repo, 165 tracked files

one directory, added to your repo

The structure

emberfall/ — the working treeassets/ config/ docs/ src/ tests/ tools/ CMakeLists.txt README.md CHANGELOG.md ... ← your files. untouched, byte for byte. .dotworld/ ├── dots/ ← one .dot.md per file — DURABLE │ ├── src/gameplay/combat/CombatSystem.cpp.dot.md │ ├── docs/gdd/combat.md.dot.md │ └── … 165 dots, 165 files ├── properties.json ← this repo's vocabulary — DURABLE ├── dotworld.config.json ← which plugins are attached — DURABLE └── derived/ ← index, embeddings, graph — DISPOSABLE ├── embeddings/ graph/ hashes/ orphans/ comms/ └── .gitignore contains a single line: *

No database. No server. No sidecar format.

A source file keeps its raw bytes — no frontmatter injected, no marker comment. Someone who has never heard of dotworld can read this repo and never notice it.

Delete .dotworld/derived/ at any time. It is recomputed from the files beside it on the next index. Nothing in it is a cache and nothing in it is truth.
what reaches your remote

Committed, or not — you choose, and the default is "not"

pathin git?why
your source files tracked Nothing changed. dotworld never writes to them.
.dotworld/dots/ tracked, optional push Durable metadata. Versions with the file, merges with the file, reviews with the file — that is the whole point. Whether it leaves your machine is a separate decision.
.dotworld/properties.json
.dotworld/dotworld.config.json		 tracked, optional push The repo's property vocabulary, and the plugin composition. Same treatment as the dots — and they live inside .dotworld/ precisely because that is the directory the pre-push filter strips.
.dotworld/derived/ never Self-ignoring — it ships its own .gitignore containing *.
A repo dotworld has just met is local by default. The first source_register installs a pre-push hook, and a plain git push then strips .dotworld/** before it reaches the remote. Your metadata is committed and versioned locally; your teammates see nothing until you opt in with neverPushDotworld=false.

dotworld · 03

The dot

A file is the content — whatever you wrote, byte for byte. Its dot is what dotworld knows about it. Two files, both durable, both in git.

the file: src/gameplay/combat/CombatSystem.cpp

the metadata file itself

A dot is markdown with frontmatter — nothing more

.dotworld/dots/src/gameplay/combat/CombatSystem.cpp.dot.md--- id: src/gameplay/combat/CombatSystem.cpp title: CombatSystem tags: [] source_path: $DOTWORLD_ROOT/src/gameplay/combat/CombatSystem.cpp kind: code summary: 'Implementation of CombatSystem. tryMeleeAttack() gates on a stamina check but does not yet consume stamina… resolveDamage() applies a 1.1x multiplier for Fire…' summary_hash: 46fd70cd5dd2f056ccf9334b9a1db518b261cd8c reviewStatus: changes-requested riskLevel: high reviewedBy: - combat-reviewer lastHumanReview: '2026-06-01' --- combat-reviewer: Confirmed the honest gap flagged in DamageTypes.h — resolveDamage() has a TODO for Corrosion/ Static that falls through to raw damage.amount with no status-effect tick… Leaving reviewStatus=changes-requested to reflect real unfinished work, not a doc nit.

reserved identity

id, source_id, source_path, title, tags — these are not properties. They cannot be set through the property commands, and they never enter the property bag.

built-in properties

kind, summary, summary_hash, obsolete, render-hint, agent_instructions — what the kernel and the shipped plugins write. Available in a fresh repo with nothing declared.

this repo's own properties

Everything highlighted. Arbitrary keys this repository declared for itself. dotworld ships no opinion about what they mean.

the body

Free prose under the frontmatter, authored by a human or an agent. It merges line-by-line, so two reviewers on two branches both keep their note.

what a property is

A key is declared before it can be used — and the declaration says how it merges

.dotworld/properties.json  ·  the repo's vocabulary — durable, in git{ "reviewStatus": { "merge": "last-writer", "description": "Review workflow state for this file: needs-review | in-review | approved | changes-requested. Set during triage; the review-gate process reads it to find what still needs attention." }, "reviewedBy": { "merge": "union", "description": "Set of reviewer ids who have signed off. Union-merged so parallel reviewers on separate workspaces each add their own id without conflicting." } }
merge strategysettles a divergence by
last-writertaking the newer value. For a state that has exactly one correct answer.
unionkeeping both sides' members. For a set — reviewers, owners, dependencies.
line-unionkeeping both sides' lines. For accumulating free text.
countersumming the deltas. For something CI increments from two machines.
The declaration is why a merge is quiet. Two reviewers, two branches, both adding themselves to reviewedBy — git sees a conflict, dotworld already knows the answer is the union and never asks you.
the commands that touch a property

Declare it, set it, find it

$ dot property_register name=lastHumanReview \ merge=last-writer \ description='ISO date a human last meaningfully reviewed this file end-to-end — read it, judged it correct, not just skimmed a diff.' $ dot property_set file=src/core/EntityManager.cpp \ key=lastHumanReview value='"2026-05-14"' --user debt-builder { "ok": false, "error": "`lastHumanReview` is not registered in this working tree (source 'emberfall'), and is on no dot there either. Otherwise register it here first — `property_register name=lastHumanReview …`", "code": "BAD_PARAMS" } ← the refusal names the fix
property_registerDeclare a key in this repo's vocabulary, with its merge strategy and what it is for. property_setWrite one key on one file's dot. The source file is never touched. property_getRead named keys off named files. property_unsetRemove a key from one dot. An explicit choice, so it works even on an unregistered key. property_unregisterWithdraw a declaration. Values already written stay on their dots. property_listThis repo's whole vocabulary — what is declared, and what is actually in use. search_propertiesThe reason any of this exists: which files have riskLevel=high?
An unregistered key is refused at write time. Otherwise you get lastHumanReview, LastHumanReview and last_human_review in one repo by Q3, and every reader has to guess which spelling is canonical.
how the two files find each other

The path is the identity

the mapping is mechanical — mirror the path, append .dot.mdsrc/gameplay/combat/CombatSystem.cpp │ └─▶ .dotworld/dots/src/gameplay/combat/CombatSystem.cpp.dot.md and the dot says so about itself: id: src/gameplay/combat/CombatSystem.cpp source_path: $DOTWORLD_ROOT/src/…/CombatSystem.cpp ↑ relative to the source root, so a clone at any path resolves it identically emberfall @ master: 165 tracked files · 165 dots

No id column, no join table, no lookup service. If you can name the file you can name its dot, and vice versa — which is also why a dot is never addressed by its own path.

So what happens when the file moves?

Renaming a file by hand would strand its dot at the old path. dotworld asks git — the same rename detection git log --follow uses — and moves the dot to match. Your metadata survives a refactor you did with mv.

When git genuinely cannot tell (the file was rewritten as it moved), the dot is reported stranded rather than silently dropped, and dot_attach is the manual half — you name the new path, the dot follows.

The failure mode this rules out: a year of accumulated review state, ownership and provenance quietly detaching from a file because someone reorganised a directory.

the one worth a slide of its own

A workspace is a git worktree, so parallel agents stop colliding

$ dot workspace_list sourceId=dotworld { "name": "dotworld", "kind": "canonical", "path": "/home/dragonlord/dotworld", "dirty": 11, "unlanded": 0 } ← the shared checkout { "name": "config-401", "kind": "managed", "branch": "users/config-401", "path": "~/.dotworld/worktrees/dotworld/config-401", "dirty": 21, "unlanded": 0 } { "name": "issue-399", "kind": "managed", "branch": "users/issue-399", "dirty": 0, "unlanded": 1 } ← done, not merged yet { "name": "issue-400", "kind": "managed", "branch": "users/issue-400", "dirty": 4, "unlanded": 0 }

Four agents, four checkouts, four branches, one repository.

workspace_open creates the caller's own worktree on their own branch, outside the source root. workspace_submit merges it back into the canonical checkout wherever that lives.

Because a workspace is a real worktree, none of this is a dotworld abstraction you have to learn. Your editor, your test runner and your git all work in it unchanged.

Conflicts stay git's. dotworld reports the conflicted paths, exactly as git does, and you settle them in your own workspace. It never hands back a payload with both sides in it for you to answer. What it does do is conflict less — the per-property merge strategies resolve divergences git would have stopped on.
dotworld · 05

Plugins

Local, detachable modules that may hold a model and credentials. Everything in dotworld that needs an LLM is one of these — which is what keeps the kernel free of both.

four shipped: obsolescence · summarizer · comms · context-loader

how one hooks up

Named in a config file, loaded at boot, contributes commands

.dotworld/dotworld.config.json  ·  composition is declared, never discovered{ "plugins": [ { "id": "obsolescence", "engine": "rule-based", "settings": { "rules": [] } }, { "id": "summarizer", "engine": "claude-code", "settings": { "model": "haiku", "maxBodyChars": 12000, "timeoutMs": 60000 } }, { "id": "comms", "engine": "fs-log" }, { "id": "context-loader", "engine": "compose" } ] } a secret is NAMED, never inlined: "credsEnv": "ANTHROPIC_API_KEY"

Three moving parts.

The manifest — id, version, requiresHost, the engines it accepts, and a factory. If the config names an engine the manifest doesn't list, the plugin refuses at boot instead of half-working.

The command seam — a plugin declares contributesCommands and hands the kernel ordinary CommandDefs at boot. They then appear in dot --help, in the MCP tool catalog and over HTTP identically to a kernel command. Nothing downstream can tell the difference.

The engine seam — the one place a model may live, behind an interface. Tests inject a deterministic fake; production injects a real model; the plugin code is the same either way.

Detach it and the command is absent, not present-and-refusing. Nothing in the kernel names these plugins, so there is no stub to fall back to. plugin_list reports the live composition, and anything skipped at boot with its reason.

obsolescence — the reference plugin

command
obsolescence_review

rule-based — the seam is ObsolescenceJudge, so a real LLM drops in behind it

it may — that is why it is a plugin

Why it is the reference. Candidate generation, judgment and the file rewrite all live outside the kernel, composing primitives any consumer could compose. Nothing was added to the kernel to make this plugin possible.

You point it at a decision. It finds every note that decision contradicts.

A confirmed correction edits the actual file — never a read-time overlay that makes a document mean something different depending on who reads it.

Every edit lands as unlanded commits on the plugin's own branch, users/obsolescence. That branch is the review surface. git diff ref=users/obsolescence is the diff, git merge accepts it, git branch -D throws it away.

The supersedes edge it writes is provenance, not truth — a record of what replaced what, queryable through graph_provenance.

Nothing in the kernel models a review queue, an approval state or a proposal. A branch already is all three.

The split is exact. The kernel detects the drift: it stamps summary_hash with the body the summary was written against, so a stale summary is a hash comparison, not a judgment. What the summary should now say needs a model — so it cannot live in the kernel at all.
every dot the summarizer has touchedsummary: 'Implementation of CombatSystem. tryMeleeAttack() gates on a stamina check but does not yet consume stamina, animate, or do hit detection (TODO)…' summary_hash: 46fd70cd5dd2f05…

The hash is the body this sentence was true of. Edit the file and the hash no longer matches — the summary is now suspect, mechanically, with nobody having to notice.

summary_refresh rewrites only the ones that no longer match. On a repo of thousands of files that is the difference between a nightly job and an unaffordable one.

Why it is a plugin and not a command. It computes nothing new — it is formatting convenience over two existing sources of truth. That is exactly the kind of thing the kernel should not grow.

Point it at a list of files, or at an index, and get one prompt-ready blob.

A hand-maintained context document goes stale the moment someone renames a file, and nobody finds out until an agent confidently reasons from a paragraph about code that no longer exists.

An index is an ordinary file that is a list of links (index_create writes one). Point context_load at it, and maintaining your agent's context means pruning that list — not rewriting a document.

Prune the index, not the document.
writing your own

What a plugin actually costs you

src/plugins/<your-plugin>/ manifest.ts — what it is, and how to build it plugin.ts — what it does // manifest.ts export const yourManifest: PluginManifest = { id: 'your-plugin', version: '1.0.0', requiresHost: '^1.0.0', engines: ['offline', 'real'], factory({ app, engine, settings }) { if (engine !== 'offline' && engine !== 'real') throw new Error(`unknown engine '${engine}'`); return { instance: new YourPlugin(app, engine) }; }, }; // plugin.ts — the command seam contributesCommands(): CommandDef[] { return [{ name: 'your_command', meta: { …params… }, handler: async (ctx, args) => { … } }]; }

Four rules, and they are the whole design.

1 · Compose kernel primitives. If you need something the kernel doesn't expose, argue for a general primitive any consumer could use — never kernel code that knows your plugin's name.

2 · Put the model behind an engine seam. Ship a deterministic offline engine as well. That is what makes the plugin testable without a network, and what lets someone swap your model for theirs.

3 · Write to files, or to a branch. No new store. If your output is a proposal, land it on your own users/ branch and let git be the review queue.

4 · Declare your properties. If you write metadata, property_register it with a merge strategy — otherwise your keys will refuse to auto-resolve the first time two workspaces diverge.

Then name it in the config. Your command appears in the CLI, the MCP tool catalog and the HTTP surface at once, because all three are generated from the same registry.
dotworld · 06

Faces, the waist, and satellites

The same commands reach you three ways. Between any remote caller and the kernel there is exactly one door — and today it is standing open on purpose.

three faces, one command set

Today we are only using one of them

CLI this deck

cli.ts · a human at a terminal

The only face with a working directory, so it is the only one that can infer which source you mean from where you are standing. Everything you will see for the rest of this deck is dot <command> key=value.

dot --help is generated from the command registry, so the interface contract cannot drift from the code.

MCP not today

mcp-server.ts · an agent

The tool catalog is generated from the same registry. Every command's description is the tool schema — when the caller is a model, that text is the API.

Fully built and running. Left out of this deck so the demos read as commands you could type yourself.

HTTP not today

http.ts · a service

No working directory, so it never infers a source — the caller names one explicitly or gets an error.

The face a remote caller would actually arrive through, which is why the next slide matters.

One registry, three faces, generated. A command cannot exist in one face and not the others, and a parameter cannot be honoured but undeclared — dispatch refuses any key no command declares, naming the ones it has. A silently dropped parameter is indistinguishable from one you never passed, and most parameters have defaults, so you would get ok: true and an answer computed from a default you did not choose.
the waist, and what is beyond it

One door — currently unlocked, deliberately

auth modewhat it means
none default No credential required. Every command runs as the fixed user local. This is what is running today, and it is the right answer for a single person on their own machine.
managed A bearer key maps to a user. Built and tested; refuses to start with no keys rather than falling back to open.
proxy A trusted upstream asserts the identity in a header. Requires a shared secret — without one the header is not trusted, it is merely believed.
The identity is not a label. It becomes the git author of durable commits, a branch name, and a directory path. That is why a mode that cannot be honoured throws at startup instead of quietly degrading — and why none being the default is a deployment choice, not a missing feature.

Satellites — the layer that is designed, not built.

A satellite is a remote, API-only capability: something that runs somewhere else and reaches dotworld over the network. None exist yet.

The distinction that makes the layer worth naming is where the traffic goes. A plugin is local — it sits beside the files and bypasses the waist, and that locality is its definition. A satellite is remote, so it has no choice but to cross the waist like any other caller.

Which means the work to support satellites is not new architecture. It is turning on a mode that already exists, and running a face that already ships.

The kernel holds no model and no secret. It is the waist.
use case · 1 of 7

Flaky Test Triage

A test fails intermittently. Someone mutters “yeah, that one's flaky” and re-runs the build. The knowledge lives in Slack scrollback, or in nobody's memory at all.

Flake dashboards (BuildPulse, Trunk) hold the data outside the repo — a snapshot, on someone else's server.

You can't diff a dashboard. You can't bisect it. You can't review it in a PR.

use case · 2 of 7

Review Debt

Mira runs the team. She wants one thing: the files that have gone longest without a human reading them end to end, weighted by how much they've churned since.

Git knows who changed a file. It does not know who read and judged one. Review approvals live in the forge, attached to pull requests, and expire from view the moment the PR closes.

There is no lastHumanReview field. Not in the code, not in CI, not in any dot. It has to be invented.

This is the greenfield demo: what happens when the property you need doesn't exist yet.

repo: dotworld-demo · branch: demo/review-debt · baseline: master @ 4d24e97

1 · the initial state

src/gameplay/save/SaveGame.cpp — before

.dotworld/dots/src/gameplay/save/SaveGame.cpp.dot.md  ·  on master--- id: src/gameplay/save/SaveGame.cpp title: SaveGame — implementation tags: [save, gameplay, serialization, stub] kind: code reviewStatus: changes-requested riskLevel: high reviewedBy: - save-reviewer summary_hash: 9f318039794e665af96… --- save-reviewer review note: save() calls writeInventoryBlock() and writeWorldFlags…

A reviewer has been here. The dot already records what they concluded — risk is high, changes requested, save() returns true even when nothing was written.

What it does not record is when. A year-old "changes-requested" and a yesterday-old one look identical here, and only one of them is still trustworthy.

Remember this file. It is about to become the worst file in the repo, and then the best.

Context Budgeting

Ask an agent how input handling maps keys to actions and it can find every plausible file in the engine — main loop, ECS, render, audio, input, physics. That's 14 files in this repo's core surface alone.

Grep and embedding search return matches, not a budget. Every candidate still costs a full read to rule out, and nothing tells the agent that cost before it pays it.

You can find every file. You still don't know what any of them cost to open.

Every source file gets a dot: a markdown sidecar with YAML properties, living in .dotworld/, tracked in git like any other file. Entity.h is 680 bytes — a POD struct: a generation-tagged index handle used as the ECS's opaque reference to a live or dead slot.

2 · what we ran · commit adfcc5e

tokenCount is the only property this demo had to add

dotworld already reports whether a summary is still true: summary_hash is a sha1 of the source bytes, and dot_get compares it live. Nothing to register for that half.

$ dot property_register name=tokenCount \ merge=last-writer \ description="Estimated tokens to load the full file: ceil(bytes/4). Maintained by tools/token-stamp.sh so agents can budget context before opening a file." # the only writer of tokenCount — tools/token-stamp.sh bytes=$(wc -c < "$f") tokens=$(( (bytes + 3) / 4 )) dot property_set file="$f" key=tokenCount \ value="$tokens" --user "$user"
summary_hash and summaryStatus needed no property_register call at all. They're native to dot_get. The team registered exactly one thing.
.dotworld/properties.json  ·  this demo's one entry{ "tokenCount": { "merge": "last-writer", "description": "Estimated tokens to load the full file: ceil(bytes/4). Maintained by tools/token-stamp.sh so agents can budget context before opening a file." } }

use case · 4 of 7

Document Obsolescence

When code changes and its documentation doesn't, nothing anywhere records that the doc is now lying. The file's timestamp is old, its diff is empty, and it reads as confidently as the day it was true.

This repo has already been burned once: a postmortem in docs/postmortems/alpha-postmortem.md has a section titled "documentation drift" about save-load.md describing v3 after the code had moved to v4.

You cannot grep for "documentation that is quietly wrong."

repo: dotworld-demo · branch: demo/doc-obsolescence · baseline: master @ 4d24e97

1 · the initial state

docs/systems/save-load.md — before

.dotworld/dots/docs/systems/save-load.md.dot.md  ·  on master--- id: docs/systems/save-load.md title: 'Engine Module: Save/Load' kind: prose summary: 'Design doc for Emberfall's save/load system. … correctly states the current format as version 4 (Vael Spire discovery flags) with version 3 as the minimum supported via an upgrade pass …' summary_hash: f857b2b5e01e25c082c09fd6… ---

Today this doc is correct. It describes save format v4, which is what the code actually implements.

The dot carries a summary_hash: the sha1 of the source file's bytes at the moment its summary was last verified. That one field is the entire mechanism.

Remember this file. It is about to become wrong without anyone editing a single character of it.

$ dot graph_affected seed=src/gameplay/save/SaveVersion.h { "path": "docs/systems/save-load.md", "title": "Engine Module: Save/Load", "reason": "embedding", "score": 0.9488 } ← second-highest hit, behind only the decision file $ dot graph_affected seed=docs/decisions/2026-08-20-save-format-v5.md { "path": "docs/systems/save-load.md", "reason": "embedding", "score": 0.9163 } ← second again, ahead of SaveGame.cpp and .h

Seeded on the changed header or on the new decision record, the impact graph puts save-load.md near the top of what this change touches.

Two signals, two jobs.
summary_hash → “this file moved under its summary.”
graph_affected → “this file should probably move too.”

Together they give a doc-consuming agent a policy it can actually follow: trust current, distrust stale, and cross-check anything the graph flags after a decision lands.

use case · 5 of 7

Selective Regeneration

Last spring's docgen pass over docs/systems/*.md ran on quill-mini-2 because it was cheap. Three docs got manually flagged as too vague or wrong and re-run on quill-pro-1; the other ten shipped as-is.

Which three? Nobody wrote it down — it lives in old PR threads and people's memory. Now quill-pro-1 has gotten cheaper and better, and someone wants to "just regenerate the docs."

Re-running all 13 through the new model costs real money and throws away the diffs on the docs that already got the good model.

2 · what we ran · commit 8a31b56

Register provenance properties, then backfill last spring's run

dotworld refuses property_set on a key nobody registered, so the four generation-provenance fields have to exist in the schema before 13 files can be backfilled.

$ dot property_register name=genModel merge=last-writer \ description="Which generation model produced this artifact (e.g. quill-mini-2, quill-pro-1). Set by the docgen pipeline." $ dot property_register name=confidence merge=last-writer \ description="Self-reported confidence (0-1) the generation model logged at generation time. Low values are candidates for regeneration." $ dot property_set file=docs/systems/audio.md \ key=genModel value='"quill-mini-2"' --user regen-planner $ dot property_set file=docs/systems/audio.md \ key=confidence value=0.58 --user regen-planner
Same pattern for promptVersion and costUsd. All four are merge=last-writer — each is a single fact about the latest generation, not something two branches should ever need to combine.
.dotworld/properties.json  ·  this demo's 4 properties{ "confidence": { "merge": "last-writer", "description": "Self-reported confidence (0-1) the generation model logged for this artifact at generation time. use case · 6 of 7

Cross-Repo Impact

Emberfall (the engine) and Emberfall Forge (a level editor built on top of it) are not a monorepo. Forge is a standalone fork that vendors copies of the engine's public interfaces — src/core, src/gameplay/save, src/input — into its own tree, with its own git history.

Change something in the engine and grep -r inside the engine repo finds every in-repo caller. It cannot see Forge's copy — that's a different clone, on a different machine, in a different .git. Six dotworld sources are registered on this machine (dot source_list); a local search reaches exactly one of them.

You can't grep a repo you haven't cloned.

2 · what we ran · commit be1dd04 (emberfall-forge)

Declaring a dependency writes a real file — in the dependent's repo

The property isn't registered where the engine lives. It's registered where the knowledge of the dependency lives — in Forge, by whoever vendored the code.

$ dot property_register sourceId=emberfall-forge \ name=dependsOn merge=union \ description="Files in the engine (emberfall) source this file's correctness depends on… values are strings of the form \"emberfall:<path>\"." { "ok": true, "result": { "name": "dependsOn", … } } $ dot property_set sourceId=emberfall-forge \ file=src/editor/EditorApp.cpp key=dependsOn \ value='["emberfall:src/gameplay/save/SaveVersion.h", "emberfall:src/gameplay/save/SaveGame.h", "emberfall:src/core/EntityManager.h"]' { "ok": true }
Nothing in the engine repo changed. The edge lives entirely on the dependent's side — which is the only side that actually knows it exists.

use case · 7 of 7

Onboarding

Day one on Emberfall: access to two repos, emberfall (the engine) and emberfall-forge (the level editor, forked from it). 165 tracked files each side. Real questions on day one: where does saving happen, can I trust it, how do input bindings work, what's the riskiest code to read first?

grep and an IDE will find you the code. Neither tells you which of it survived review, who owns it, or whether a function that returns true actually means success.

You can grep for save(). You can't grep for "don't trust this."
